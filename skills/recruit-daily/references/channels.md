# 寻源命令与坑（仅 BOSS 直聘）

> 本工作区**只用 BOSS 直聘**，不装也不跑 `liepin-cli`。下文若还出现其他招聘平台的说法，一律忽略。

命令细节的权威是 `boss help`；这里只放**编排流程实际用到的调用形态**和实测踩过的坑。
CLI 驱动本机真实浏览器（Chrome/Edge），需要先跑一次 `boss login` 扫码登录，登录态持久化。

## Boss 直聘（上游 `@joohw/boss-cli`，当前 0.6.6）

> 装：`npm install -g @joohw/boss-cli`，然后 `boss login` 扫码登录（登录态持久化）。
> 命令细节的权威是 `boss help`；下面只放**编排流程实际用到的调用形态**和实测踩过的坑。
> ⚠️ 上游 search **只有关键词，没有筛选参数**；`greet` 按姓名、没有 `--index/--dry-run`。
> 别把别的 fork/魔改版文档套到这里。

| 目的 | 命令 |
|---|---|
| 查未读 | `boss list --unread`（角标 > 0 才有） |
| 常规搜索（**姓名打码**，全网牛人） | `boss search <关键词>`（仅关键词，无筛选） |
| 推荐池（**姓名不打码**，按岗位圈定） | `boss recommend <岗位关键字>` |
| 推荐页逐名打招呼 | `boss greet <姓名> --job <岗位关键字>` |
| 深度搜索 / 匹配 | `boss deep-search [岗位关键字] [--core <核心要求>] [--bonus <加分项>] [--match]` |
| 在线简历预览（**耗每日查看额度**，按需） | `boss preview <姓名>` |
| 打开会话 / 取简历 | `boss chat "<姓名>"` → `boss action resume` |
| 核对职位与开放状态 | `boss positions` / `boss jd <名称>` |

关键行为与坑（上游 0.6.6 实测）：
- **`boss search` 只接受 `[关键词]`**，不接 `--job/--age/--degree/--city` 等任何筛选参数，传了直接吐用法错误。
  搜索页**做不了硬规则筛选**——年龄/学历/岗位的口径收窄靠两条路：
  ① 用 `boss recommend <岗位>`（推荐池按岗位圈定、姓名不打码）；
  ② 按关键词搜出列表后，**在本地对照 CONTEXT 硬规则初筛**（`recruit-today` 会提示哪些人还没过硬门槛）。
- **`boss greet` 只有 `greet <姓名> [--job]`**，没有搜索池的 `--index`、没有 `--dry-run`。
  搜索池（姓名打码）**无法直接打招呼**——要主动联系，走推荐池 `boss greet <姓名> --job <岗位>`。
- **`boss greet` 须当前已在推荐页/深度搜索页且列表已加载**；不会自动跳转。消耗打招呼次数、单次成本较高、不可撤回。
- **`boss preview` 不支持 `--job`**，传了会被拒；须已在推荐/深度搜索/常规搜索页且列表已加载。
- **`boss positions` 可核对平台当前职位及开放状态**；`boss jd <名称>` 可读取单岗详情。
  招聘优先级与已梳理标准仍以 `CONTEXT.md` 为准，不能把平台开放职位自动当成已批准寻源岗位。
- **`boss recommend` + `boss greet <姓名>` 更稳**：推荐页按岗位圈定、名字不打码可精确打。
  循环打太快撞列表刷新会偶发失败，间隔 ≥3s + 失败重试一次即可。
- **`boss chat` 支持 `--index <序号>`**（按 list 输出的序号开会话）+ `--unread` + `--strict`，可用于已建立联系的候选人。
- **取简历**：顺序执行、每批 3-5 人；失败加 `--strict` 重试，仍失败标"未获取"，别反复重试烧时间。
- ⚠️ **对外动作命令，本工作区一律不用**（都不可撤回，需用户逐次授权）：`boss send`（发消息）、
  `boss action request-attachment-resume`（求简历，会向对方发默认话术）、`boss action not-fit`（点不合适）。

## 渠道分工（BOSS 单渠道版）

BOSS 有三个入口，能力不同（上游 0.6.6）：

- **常规搜索**（`boss search <关键词>`，姓名打码）：广撒网找全网牛人。**只能按关键词**，无筛选、**不能直接打招呼**——当储备池，捞出后在本地硬规则初筛。
- **推荐池**（`boss recommend <岗位>`，姓名不打码）：按岗位圈定的本地池，**可以精确打招呼**（`boss greet <姓名> --job`）。主动联系走这里。
- **深度搜索**（`boss deep-search [--core ...] [--match]`）：带核心要求/加分项的结构化匹配，`--match` 才消耗今日匹配次数。

所以「打招呼」只能走推荐池或深度搜索页；常规搜索命中的人要联系，需先在推荐池找到对应的人。

哪个岗位哪个入口肥，是**跑出来的结论不是猜的**：每轮寻源后把"某岗某入口有效/无效"的观察
写进 `CONTEXT.md`（沉淀在"已对齐决策"或岗位表备注），下轮按结论分配精力。
没有结论之前，搜索 + 推荐两个入口都跑。

## 默认有头，绝对不要改成无头

| 平台 | 默认 | 依据 |
|---|---|---|
| **BOSS** | **有头**（真窗口，启动抢一次焦点） | 2026-08-19 实测：无头被判成「第三方辅助工具」并限制 web 端登录 |

所以跑 `boss` 命令时屏幕上出现 Chrome 窗口**是正常的，不是故障**，不要去"修"它。

### ⛔ 禁止事项：不要开无头

不要设 `BOSS_BROWSER_HEADLESS=true`，也不要设 `RECRUIT_BROWSER_HIDDEN=true`
（后者是统一覆盖开关，同样会拖进无头）。

即使用户抱怨窗口抢焦点、即使你觉得无头更清爽、即使某个命令在无头下跑得更顺——**都不要开无头**。
真要开，必须用户明确说「我知道有封号风险，开无头」。

**理由（两个独立样本）：**

- **BOSS，2026-08-19**：一个账号被**限制 web 端登录 24 小时**，页面文案明确写「系统检测到您的
  账号存在使用第三方招聘管理系统、插件、外挂、软件等辅助工具」——判定的是**工具指纹**，
  不是打招呼频率。
- **BOSS，同期**：另一个团队用上游 boss-cli（默认有头）长期没事，**他们的 AI 擅自改走无头版
  之后当天封号**。

**根因**：无头 Chrome 的 `User-Agent` 自报 `HeadlessChrome/<ver>`，而 Client Hints
仍说 `Google Chrome`，这个自相矛盾是零误报的自动化信号。作者**刻意不伪装 UA**（伪装与
「不做识别不出自动化方向的对抗」这条红线冲突），所以绕不过去，只能不用无头。

抢焦点是体验问题，**账号被限是业务问题**。想看画面用 DSH 面板（下一节），不是翻回无头。

BOSS 被限期间的好消息：限制**只针对 web 端**，用户可以用 BOSS直聘 APP 或 PC 客户端照常招聘。

### 想看浏览器在做什么

用 **DSH「招聘浏览器」面板**——Web UI 右侧的实时画面，不抢焦点。**默认折叠、默认只读**：
看画面安全，但在面板里手动操作有实测风险，见下方警告。

### 关掉常驻浏览器

```bash
boss shutdown       # 关 Boss 的浏览器（名字不是 quit —— 交互模式里 quit 是退 REPL）
```

浏览器**跨命令常驻**（命令结束只断 CDP），所以面板能一直连着；
上面这两条命令也是跑完招聘想释放内存时的出口。**换了环境变量不会让已在跑的那只切换模式**，
得先关掉，下条命令才会按新模式重启（登录态在 profile 里，不丢）。

**判断在跑的那只是什么模式**：`curl http://127.0.0.1:53470/json/version`，
返回的 `User-Agent` 含 `HeadlessChrome` 就是无头——**看到无头就应该关掉它重启成有头**。

## ⚠️ 面板里手动操作有实测风险，优先走 CLI

**根本原因：boss-cli 的反检测保护挂在 CLI 进程自己的 CDP session 上，进程一退出就全部失效。**

那套保护有四层（拦风控 SDK 脚本、把 6 个上报端点用 204 假装成功、注入页面守卫、`navigator.webdriver`
等一堆改写），另加 fork 自己写的三重熔断。2026-08-18 实测确认：**CLI 进程一断开，`Fetch.enable`
拦截立刻撤销，`addScriptToEvaluateOnNewDocument` 注入的守卫也随之移除，一层不剩。**

所以真实的边界不是「CLI 模式 vs 面板模式」，而是**命令执行的那几秒 vs 其余所有时间**。浏览器跨命令
常驻，命令跑完它就完全裸奔——面板操作、host 发起的导航，全都在裸奔时段里。

**已发生两次账号限制（同一账号，2026-08-18）：**

| 触发动作 | 后果 |
|---|---|
| 排查时并挂第二个 host + 反复切贴合（页面秒级反复 resize） | 限制约几小时 |
| 点面板的「有头/无头切换」（同一会话内 UA 在 HeadlessChrome 与 Chrome 之间突变） | **限制 24 小时** |

**因此现在的规则：**

- **打招呼、拉列表、读简历这些日常动作一律走 CLI 命令**，别在面板里手点。面板用来看，不用来操作。
- 面板**默认折叠、默认只读**。展开会让 host 持续订阅画面并开启崩溃自愈；要手动操作得先按工具栏的
  🔒 显式切成可操作。
- **有头/无头切换按钮已摘掉**，而且默认已经是有头，正常情况下不需要切什么模式。
- **账号被限期间（页面出现 403 / verify / security-check）什么都别做**。host 现在会自动熔断：
  停掉自愈重启、停掉贴合重发、拒绝一切导航与启动，面板顶部显示红色提示条。**人工处理完再点解除。**
  在限制期内继续访问会把恢复时间一路延长（实测：`boss shutdown` 之后 16 秒就被自愈拉回来过）。

## 浏览器 / 稳定性坑

- **并发连同一个调试端口本身没问题，但别从第二个会话 enable 重量级 CDP 域**。
  DSH 的「招聘浏览器」面板就是长期并发挂在同一个端口上的，只用 `Page.enable` + screencast +
  `Input.*`，稳定工作。真正会出事的是从第二个会话发 `Runtime.enable` / `Network.enable`：
  前者被 BOSS 反爬当成调试器挂载信号、会**杀掉整个浏览器**（实测 0/4 存活），后者会把会话
  拧死（`Network.enable timed out`），之后 boss 命令报超时。
  写诊断脚本时：读页面用 `Runtime.evaluate`（不需要 enable），别图省事开 domain。
- **恢复方法**：结束掉 CLI 拉起的那个浏览器主进程（登录态在 profile 里持久化），下条命令自动重启且仍登录。
- **后台跑批量 greet 别用管道过滤**（`| sed` / `| tail`）再落文件——管道要等 EOF 才输出，
  会误判"空/卡住"；要么前台跑给足超时，要么全量落文件事后再筛。
- **平台改版高频**：选择器失效、新弹层出现是常态。命令报错先升级 CLI（`npm update -g`），
  再看是不是平台改版，别自己写浏览器脚本硬闯。

## 登录等待

上游 `boss login` 不等待人工扫码。agent 需要等待时使用：

```bash
node workbench/boss-login-wait.js
```

脚本验证成功后才返回；不要自行 sleep/poll。

## 推荐列表去重

上游推荐页卡片根节点选择器可能把嵌套节点算成两张卡片，导致同名重复。安装或更新 boss-cli 后运行：

```bash
node workbench/patch-boss-cli.js
```

补丁会过滤被其他根节点包含的子节点，只保留真正的卡片。

## 未读列表增强

补丁后的 `boss list --unread` 会滚动加载列表，并输出稳定 ID。后续打开会话优先使用：

```bash
boss chat --id <稳定ID> --unread
```

稳定 ID 仍需在执行前确认对应候选人；如果消息或列表发生变化，工作台会通过 inbox signature 拒绝继续操作。
